# Linux Network Connectivity and DNS Troubleshooting

## 1. Project Overview

This project documents a structured investigation of network connectivity, DNS resolution, IPv4/IPv6 routing, TCP connectivity, TLS negotiation, and HTTP responses in a Kali Linux virtual machine.

The objective was to examine the network stack layer by layer, collect evidence, distinguish successful operations from configuration limitations, and avoid making unsupported root-cause assumptions.

**Investigation date:** November 6, 2026
**Environment:** Kali Linux virtual machine
**Network interface:** `eth0`
**Network manager:** NetworkManager

## 2. Investigation Scope

The investigation covered:

- Network interface state and IPv4 addressing.
- Default gateway and route selection.
- ICMP connectivity.
- System name resolution.
- DNS over UDP and TCP.
- Direct DNS queries to an external resolver.
- IPv4 and IPv6 connectivity.
- TCP port accessibility.
- TLS handshake and certificate verification.
- HTTP responses and redirects.
- HTTPS connectivity with explicit DNS resolution bypass.

All tests were diagnostic and read-only. No network configuration was modified.

## 3. Network Topology

Simplified observed topology:

```text
              External Network
                     |
              VMware Gateway
                     |
                 Virtual NIC
                     |
                  eth0
                     |
                 Kali Linux
                     |
              Docker Bridge
               (linkdown)
```

The virtual machine received a private IPv4 address through DHCP and had an IPv4 default route through its VMware virtual gateway.

The Docker bridge interface was present but reported `DOWN` and `NO-CARRIER`.

## 4. Investigation Methodology

The investigation followed a layered troubleshooting workflow:

```text
Interface
    |
IPv4 Addressing
    |
Routing
    |
ICMP Connectivity
    |
DNS Resolution
    |
TCP Connectivity
    |
TLS Negotiation
    |
HTTP Response
```

Each layer was tested independently where possible.

The investigation distinguished between:

- Name resolution failure.
- Routing failure.
- TCP connection refusal.
- Connection timeout.
- TLS negotiation or certificate errors.
- HTTP application responses.

A successful test at one layer was not treated as proof that every higher layer was working.

## 5. Interface and Routing Investigation

### Interface state

Command:

```bash
ip -br link
ip -br addr
```

Observations:

- `eth0` was operational and had an IPv4 address.
- The loopback interface was available.
- `docker0` was present but had no active carrier.

### Routing table

Command:

```bash
ip route
ip route get 1.1.1.1
```

Observations:

- An IPv4 default route was present.
- External IPv4 traffic was routed through the VMware gateway.
- The selected outgoing interface was `eth0`.
- The source address was the VM's assigned private IPv4 address.

### ICMP tests

Commands:

```bash
ping -c 4 <default-gateway>
ping -c 4 1.1.1.1
```

Results:

| Target | Packets received | Packet loss |
|---|---:|---:|
| Default gateway | 4/4 | 0% |
| External IPv4 address | 4/4 | 0% |

**Assessment:** Local gateway reachability and external IPv4 ICMP connectivity were successful during testing.

## 6. DNS Investigation

### Resolver configuration

Command:

```bash
cat /etc/resolv.conf
```

The resolver configuration was generated by NetworkManager and referenced the VMware virtual gateway as its DNS server.

### System resolver

Command:

```bash
getent ahosts archlinux.org
```

Both IPv4 and IPv6 address records were returned.

### DNS over UDP

Command:

```bash
dig archlinux.org A +noall +answer +stats
```

Result:

- A record returned successfully.
- Query time: 231 ms.
- Transport: UDP.

### DNS over TCP

Command:

```bash
dig +tcp @<configured-resolver> archlinux.org A +noall +answer +stats
```

Result:

- TCP connection to port 53 was refused.
- No DNS response was returned.

### Direct external DNS testing

Commands:

```bash
dig @1.1.1.1 archlinux.org A +time=3 +tries=1 +noall +answer +stats

dig +tcp @1.1.1.1 archlinux.org A +time=3 +tries=1 +noall +answer +stats
```

Results:

| Resolver | Transport | Result | Query time |
|---|---|---|---:|
| VMware gateway | UDP | Successful | 231 ms |
| VMware gateway | TCP | Connection refused | — |
| Cloudflare `1.1.1.1` | UDP | Successful | 99 ms |
| Cloudflare `1.1.1.1` | TCP | Successful | 71 ms |

**Assessment:**

External DNS queries worked over both UDP and TCP.

The configured virtual gateway resolver responded over UDP but refused TCP connections on port 53.

The underlying reason for this difference was not established.

## 7. IPv4 and IPv6 Investigation

### IPv4

IPv4 routing and connectivity were functional during the tests.

Evidence included:

- Successful gateway ping.
- Successful external IPv4 ping.
- Successful route selection.
- Successful TCP connections.
- Successful HTTPS requests.

### IPv6

Commands:

```bash
ip -6 addr show dev eth0
ip -6 route
```

Observations:

- `eth0` had a link-local IPv6 address.
- No global IPv6 address was observed.
- No IPv6 default route was present.

An IPv6 HTTPS request was attempted:

```bash
curl -6 -I -v --connect-timeout 5 https://archlinux.org
```

Result:

```text
Network is unreachable
```

DNS had returned an AAAA record, but the VM did not have an IPv6 default route.

**Assessment:** IPv6 name resolution was functional, but external IPv6 connectivity was unavailable in the observed configuration.

This was documented as a configuration limitation, not a confirmed network failure.

## 8. TCP Connectivity Investigation

Commands:

```bash
nc -vz -w 5 archlinux.org 443
nc -vz -w 5 archlinux.org 80
nc -vz -w 5 1.1.1.1 443
```

Results:

| Destination | Port | Result |
|---|---:|---|
| archlinux.org | 443 | Open |
| archlinux.org | 80 | Open |
| 1.1.1.1 | 443 | Open |

Netcat displayed reverse DNS lookup warnings for the destination address.

These warnings did not prevent the TCP connection checks from succeeding.

**Assessment:** All three tested TCP destinations accepted connections.

## 9. TLS and HTTP Investigation

### HTTPS to Arch Linux

Command:

```bash
curl -4 -I -v --connect-timeout 5 https://archlinux.org
```

Observed:

- TCP connection established.
- TLS 1.3 handshake completed.
- Server certificate matched the requested hostname.
- Certificate verification succeeded.
- HTTP/2 response returned.

Result:

```text
HTTP/2 200
```

### HTTPS to Cloudflare

Command:

```bash
curl -4 -I --connect-timeout 5 https://www.cloudflare.com
```

Result:

```text
HTTP/2 200
```

### HTTP redirect

Command:

```bash
curl -4 -I --connect-timeout 5 http://archlinux.org
```

Result:

```text
HTTP/1.1 301 Moved Permanently
Location: https://archlinux.org/
```

The server successfully redirected the HTTP request to HTTPS.

## 10. HTTPS Test Without Normal DNS Resolution

To isolate DNS resolution from the HTTPS connection, an explicit address mapping was supplied to curl.

Command:

```bash
curl -4 -I -v --connect-timeout 5 \
  --resolve archlinux.org:443:<tested-server-ip> \
  https://archlinux.org
```

Observed:

- The explicit hostname-to-address mapping was used.
- TCP connection succeeded.
- TLS 1.3 negotiation succeeded.
- Certificate verification succeeded.
- HTTP/2 returned status 200.

**Assessment:**

HTTPS connectivity remained successful when curl used an explicitly supplied server address instead of performing normal DNS resolution for that request.

This demonstrated that the tested HTTPS path did not depend on a fresh DNS lookup.

## 11. Findings and Root Cause Assessment

The investigation identified two notable network configuration characteristics:

**Finding 1 — DNS transport difference**

The configured VMware gateway DNS resolver answered UDP queries but refused TCP connections on port 53.

Direct queries to Cloudflare succeeded over both transports.

The reason for the gateway's TCP behavior was not established.

**Finding 2 — IPv6 routing unavailable**

The VM had a link-local IPv6 address but no IPv6 default route.

Consequently, external IPv6 connections failed with `Network is unreachable`.

**Overall assessment:**

The tested IPv4 network path was functional.

DNS resolution, external IPv4 reachability, TCP connectivity, TLS negotiation, certificate verification, and HTTP responses all succeeded for the tested destinations.

No general IPv4 connectivity outage or HTTPS failure was reproduced.

No root cause for an external application connectivity incident was established because this investigation was a baseline diagnostic exercise rather than a reproduction of a confirmed outage.

## 12. Operational Lessons

This investigation demonstrated several important troubleshooting principles:

1. A successful DNS lookup does not prove that TCP connectivity works.
2. ICMP reachability does not guarantee application-layer connectivity.
3. DNS over UDP and TCP must be distinguished during diagnosis.
4. An AAAA record does not prove that IPv6 routing is configured.
5. TCP port availability does not prove that TLS negotiation will succeed.
6. TLS success does not guarantee a successful HTTP application response.
7. Explicit address mapping can help isolate DNS resolution from HTTPS connectivity.
8. A diagnostic observation must not be presented as a confirmed root cause without supporting evidence.

## 13. Limitations

- Tests were performed from one Kali Linux virtual machine.
- Results represent the network state at the time of testing.
- No packet capture was performed.
- No real production outage was reproduced.
- The internal implementation of the VMware gateway DNS service was not investigated.
- No IPv6 configuration changes were attempted.
- No firewall or router configuration was modified.
